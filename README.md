# Маркетплейс — архитектурное проектирование

ДЗ №1 Архитектурное проектирование системы маркетплейса. Спроектирована архитектура маркетплейса, описана C4 Container-диаграммой, один сервис (**Catalog Service**) поднят в Docker и отвечает `200 OK` на `/health`. Бизнес-логики в коде нет — по условию.

## Быстрый старт

Для Docker с Compose v2.

```bash
docker compose up -d --build
curl -i http://localhost:8080/health
# HTTP/1.1 200 OK
# Content-Type: application/json
# {"status":"ok","service":"catalog-service"}

docker compose ps          # STATUS: Up ... (healthy)
docker compose down
```

Без Compose:

```bash
docker build -t catalog-service ./services/catalog-service
docker run --rm -p 8080:8080 catalog-service
```

## 2. Домены и зоны ответственности

| Домен | Зона ответственности | Чего домен **не** делает |
|---|---|---|
| **Identity (пользователи)** | Регистрация и аутентификация покупателей и продавцов, профили, роли, выпуск JWT | Не знает о заказах и товарах |
| **Catalog (каталог)** | Товары, категории, атрибуты, цены, остатки, медиа. Продавец управляет только своими товарами | Не строит выдачу для покупателя, не считает деньги |
| **Feed (лента)** | Персонализированная выдача: профиль интересов пользователя, ранжирование, fallback на популярное | Не является источником правды о товарах — хранит только проекцию |
| **Ordering (заказы)** | Корзина, оформление заказа, снапшот цены на момент покупки, статусная машина заказа | Не проводит платежи, не шлёт уведомления |
| **Payments (платежи)** | Расчёт суммы к оплате, интеграция с платёжным провайдером, возвраты, журнал транзакций | Не решает, что делать с заказом — только сообщает результат |
| **Notifications (уведомления)** | Доставка уведомлений о статусах заказов по email/SMS/push, шаблоны, настройки каналов | Не владеет статусами — только реагирует на события |

### Степень персонализации ленты

Выбран уровень, достаточный для кейса и реализуемый без ML-инфраструктуры:

1. **Профиль интересов** — веса категорий/брендов пользователя, считаются из событий `ProductViewed` (вес 1) и `OrderCreated` (вес 5) с затуханием по времени.
2. **Кандидаты** — товары из топ-категорий профиля + глобально популярные + новинки.
3. **Ранжирование** — простой скоринг: `вес категории × популярность × свежесть`, уже купленное отфильтровывается.
4. **Холодный старт** — новому пользователю отдаётся популярное.

Лента пересчитывается **асинхронно** по событиям и кладётся в Redis готовой — запрос ленты это чтение одного ключа, без обращений к другим сервисам. Если позже понадобится ML-модель, она меняет только шаг 3 внутри Feed Service, остальная система не затрагивается.

## 3. Распределение доменов по сервисам

Финальный вариант — **один домен = один сервис** (вариант B ниже):

| Сервис | Домен | Почему отдельный сервис |
|---|---|---|
| **User Service** | Identity | Нужен всем, но редко меняется; выпускает JWT, который Gateway проверяет локально по публичному ключу — User Service не вызывается на каждый запрос |
| **Catalog Service** | Catalog | Пишут продавцы, читают все; у каталога свой ритм изменений (новые атрибуты, модерация) |
| **Feed Service** | Feed | Самая высокая читающая нагрузка и самый «экспериментальный» код — должен масштабироваться и деплоиться независимо |
| **Order Service** | Ordering | Ядро процесса покупки, оркестрирует сагу заказа |
| **Payment Service** | Payments | Деньги: строгий аудит, идемпотентность, изоляция чувствительных данных и отказов внешнего провайдера |
| **Notification Service** | Notifications | Чисто реактивная, по природе асинхронная функция; сбой рассылки не должен влиять на заказы |

Плюс клиентские контейнеры — **Приложение покупателя** (Web/iOS/Android) и **Кабинет продавца** (Web SPA): у покупателя и продавца разные сценарии и интерфейсы, их можно выпускать независимо. И инфраструктурные: **API Gateway** (без бизнес-логики — TLS, проверка JWT и роли buyer/seller, роутинг, rate limiting) и **Kafka** как шина доменных событий.

**Логика разбиения:** границы сервисов совпадают с границами доменов (bounded contexts), потому что именно по ним различаются (а) нагрузка, (б) требования к надёжности и консистентности, (в) частота изменений. Между доменами мало синхронных зависимостей, поэтому сетевая граница между ними обходится дёшево.

## 4. Границы владения данными

Правило: **у каждого сервиса своя БД, в чужую БД никто не ходит**. Чужие данные получаются только через API владельца или через события — и тогда хранятся как локальная read-only проекция.

| Сервис | Владеет данными (источник правды) | Хранит проекцию чужих данных | Хранилище |
|---|---|---|---|
| User | Аккаунты, хэши паролей, профили, контакты, роли, refresh-токены | — | User DB (PostgreSQL) |
| Catalog | Товары, категории, цены, остатки, `seller_id` товара, фото товаров | — | Catalog DB (PostgreSQL) + Media Storage (S3) |
| Feed | Профили интересов, готовые ленты, счётчики популярности | Карточки товаров (из `Product*` событий) | Feed Store (Redis) |
| Order | Корзины, заказы, позиции **со снапшотом цены**, статусы, outbox | — (цену фиксирует в момент заказа) | Order DB (PostgreSQL) |
| Payment | Платежи, возвраты, журнал транзакций (append-only), idempotency-ключи | Сумма и id заказа (из `OrderCreated`) | Payment DB (PostgreSQL) |
| Notification | Шаблоны, настройки каналов, история отправок | Контакты пользователей (из `User*` событий) | Notification DB (PostgreSQL) |

Разделяемых баз данных нет. Даже там, где удобно было бы «сделать JOIN» (лента ↔ каталог, уведомления ↔ пользователи), используется проекция по событиям — это осознанная плата за независимость сервисов.

## 5. Взаимодействие сервисов

### Синхронное

| Кто → кому | Протокол | Зачем | Почему sync |
|---|---|---|---|
| Приложение покупателя → API Gateway | HTTPS/REST | Лента, каталог, корзина, заказы | Пользователь ждёт ответа |
| Кабинет продавца → API Gateway | HTTPS/REST | Управление товарами, заказы магазина | Пользователь ждёт ответа |
| Gateway → User / Catalog / Feed / Order | REST | Роутинг запросов | Пользователь ждёт ответа |
| Order → Catalog | gRPC | Актуальные цена и наличие при оформлении заказа | Нельзя оформить заказ по устаревшей цене — нужен ответ здесь и сейчас |
| Payment → Платёжный провайдер | HTTPS | Создать платёж / возврат | API провайдера синхронное |
| Платёжный провайдер → Payment | Webhook | Итоговый статус платежа | Провайдер сам сообщает результат |
| Notification → Email/SMS/Push | HTTPS | Отправка сообщений | API провайдеров синхронное; ретраи внутри Notification |

### Асинхронное (Kafka)

| Событие | Публикует | Подписчики | Зачем |
|---|---|---|---|
| `UserRegistered`, `UserUpdated` | User | Notification | Проекция контактов для рассылок |
| `ProductPublished`, `ProductUpdated`, `ProductRemoved` | Catalog | Feed | Проекция карточек, пересчёт лент |
| `ProductViewed` | Feed | Feed | Сырые события активности → профиль интересов |
| `OrderCreated` | Order | Payment, Feed | Запуск оплаты; сигнал для персонализации |
| `OrderCancelled` | Order | Payment | Возврат, если оплата уже прошла |
| `OrderStatusChanged` | Order | Notification | Уведомление покупателя |
| `PaymentSucceeded`, `PaymentFailed`, `Refunded` | Payment | Order | Перевод заказа в следующий статус |

Вне рамок системы (нет в требованиях кейса): логистика, склад, доставка, модерация.

### Сценарий оформления заказа (сага, хореография)

```
Приложение покупателя ─► Gateway ─► Order ──gRPC──► Catalog (цена, наличие)
                       │ сохраняет заказ PENDING_PAYMENT + событие в outbox (одна транзакция)
                       ▼
                 OrderCreated ──► Payment ──► провайдер ──webhook──► Payment
                                                                       │
                       ┌──────────── PaymentSucceeded / PaymentFailed ◄┘
                       ▼
                     Order: PAID / PAYMENT_FAILED ──► OrderStatusChanged ──► Notification ──► покупатель
```

Гарантии: события публикуются через **transactional outbox** (запись в БД и событие атомарны), консьюмеры **идемпотентны** (дедупликация по `event_id`), платёж создаётся с **idempotency key = order_id** — повторная доставка события не спишет деньги дважды.

## 6. Альтернативные варианты декомпозиции

### Вариант A — модульный монолит

Одно приложение, внутри модули по тем же доменам с явными интерфейсами между ними. Одна PostgreSQL, у каждого модуля своя схема. Ленты кешируются в Redis.

### Вариант B — микросервисы «домен = сервис» (выбран)

Описан выше: 6 доменных сервисов, у каждого своя БД, sync для запросов пользователя, async-события для процессов между доменами.

### Вариант C — крупные сервисы по группам доменов

Три сервиса:
- **Commerce** = каталог + заказы + платежи (одна БД);
- **Customer** = пользователи + уведомления;
- **Discovery** = лента.

---

## 7. Trade-off'ы

### A. Модульный монолит

| Плюсы | Минусы |
|---|---|
| ACID-транзакции между заказом, остатками и платежом — никаких саг и outbox | Масштабируется только целиком: под нагрузку на ленту приходится копировать и платёжный код |
| Один деплой, один репозиторий, минимум инфраструктуры — дешевле всего в разработке и эксплуатации | Один домен отказа: утечка памяти в ранжировании ленты кладёт оформление заказов |
| Нет сетевых задержек и частичных отказов между модулями | Общая БД провоцирует «удобные» JOIN между схемами — границы доменов со временем размываются |
| Легко менять границы модулей, пока домен не устоялся | Любое изменение — релиз всей системы; команды блокируют друг друга |

### B. Микросервисы «домен = сервис»

| Плюсы | Минусы |
|---|---|
| Feed масштабируется отдельно и может быть переписан (ML, другой язык) без затрагивания остальных | Конечная согласованность: заказ «висит» в PENDING_PAYMENT, пока не придёт событие |
| Изоляция отказов: упал провайдер уведомлений — заказы и платежи работают | Нужны саги, outbox, идемпотентность, DLQ — заметный объём инфраструктурного кода |
| Payment изолирован: меньше кода в контуре с платёжными данными, проще аудит | Больше движущихся частей: 6 сервисов + 6 БД + Kafka — нужны трейсинг, централизованные логи, мониторинг |
| Независимые релизы, сервисы можно отдать разным командам | Данные дублируются в проекциях; есть окно, когда проекция отстаёт от источника |

### C. Крупные сервисы

| Плюсы | Минусы |
|---|---|
| Оформление заказа с проверкой остатков — одна транзакция внутри Commerce | Commerce становится «мини-монолитом»: правка карточки товара продавцом и платёжный код в одном деплое |
| Всего 3 сервиса — проще эксплуатация, чем в B | Платёжный контур не изолирован — его отказ или уязвимость затрагивает каталог |
| Лента всё равно отделена и масштабируется независимо | Каталог (много записи от продавцов) и заказы (пиковая нагрузка в распродажи) нельзя масштабировать раздельно |
| | Группировка «Customer = пользователи + уведомления» искусственна — у доменов нет общей причины меняться вместе |

## 8. Обоснование финального выбора

Выбран **вариант B**. Аргументы опираются на требования кейса:

1. **Персонализированная лента** — самая нагруженная на чтение и самая экспериментальная часть (алгоритм будет меняться чаще всего). В B она изолирована и масштабируется независимо; в A — нет.
2. **Расчёт и учёт платежей** — требует аудита, идемпотентности и изоляции от сбоев внешнего провайдера. В B это отдельный сервис с append-only журналом; в C платежи делят процесс и БД с каталогом.
3. **Уведомления о статусах** — по природе асинхронны и не должны влиять на заказ. В B Notification только подписан на события; даже его полный отказ не мешает оформлять заказы (события дождутся в Kafka).
4. **Два типа пользователей** с разными сценариями (продавцы пишут в каталог, покупатели читают ленту и оформляют заказы) дают разную нагрузку на разные домены — раздельное масштабирование окупается.
5. **Критерий «нет разделяемых БД»** выполняется в B естественно; в A это нарушено по построению.

**Что принимаем как цену:** конечную согласованность и инфраструктурную сложность. Снижаем её стандартными средствами: transactional outbox, идемпотентные консьюмеры, idempotency key в платежах, синхронный вызов Order → Catalog оставлен ровно там, где без свежих данных нельзя (цена при оформлении).

**Когда выбор стоило бы пересмотреть:** если бы это был MVP с командой из 2–3 человек и неизвестной нагрузкой, разумнее начать с A и выделять сервисы по мере роста. Модули в A проектируются по тем же границам доменов, поэтому переход A → B остаётся возможным без переписывания доменной модели.

---

## Почему поднят именно Catalog Service

Каталог — центральный домен: от него зависят лента (проекция товаров) и заказы (цена и наличие). В рамках ДЗ сервис реализует только `GET /health`; бизнес-эндпоинты будут добавлены на следующих этапах.
